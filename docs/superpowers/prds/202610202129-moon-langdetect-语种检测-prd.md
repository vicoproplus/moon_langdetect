## 一、问题陈述

MoonBit 生态目前没有语种检测能力（`申报书-moon_langdetect-语种检测.md:17` 记载的 mooncakes.io 查重结论：以 langdetect / language detection / language identification / 语种检测 / 语言识别 / lingua / langid 等关键词检索均无语种检测项目；两个最近邻 moonlangtag 与 moonnlp 经逐一核对为互补——前者解析 BCP 47 语言标签语法而非自然语言文本，后者是通用 NLP 工具库且功能范围不含语种检测。**该结论为申报书声明，本 PRD 未独立复验**）。

多语言内容管线里，语种检测是「先判断语言、再选择分词器 / 词干器 / 排版规则」的第一跳（`申报书-moon_langdetect-语种检测.md:12,16`）：选错分词器会让索引质量立刻劣化，选错排版规则会导致显示直接出错。而语种检测必须离线、低延迟、可嵌入，调外部 API 不可行。

可移植的参照实现已经存在且可量化：上游 `langdetect` 1.0.9 内置 **55** 个语言档案文件、**184129** 条 n-gram 频率条目、合计 **2204952** 字节（`analysis/toolchain-probes.md:24-26`）；档案键长仅 1/2/3 码点（7791 / 52387 / 123951，`analysis/toolchain-probes.md:27`），非 BMP 条目 **0** 条（`analysis/toolchain-probes.md:28`）；最大档案 `ko` 23031 条 / 307193 字节，最小 `gu` 1474 条（`analysis/toolchain-probes.md:29-32`）。

若不解决，MoonBit 侧的多语言管线只能退化为字符集启发式——对同字符集语言（西语 / 法语 / 意语）完全失效（`申报书-moon_langdetect-语种检测.md:45`），或被迫引入外部服务调用，违背离线嵌入的定位。

问题的额外难点在于「行为等价」：上游存在若干非直觉但已成契约的行为——URL 正则会吞掉后续 ASCII 文本（`docs/port/upstream-behavior-contract.md` §10 quirk 2）、`cleaning_text` 里针对 Latin Extended Additional 的豁免是永不生效的死代码（同 §10 quirk 1）、空 / 纯符号输入抛异常码 5 而不是返回 `unknown`（同 §10 quirk 3；`docs/port/golden/summary.json` 的 `error_cases` 实测 18 条）。这些行为若不显式写成可验收需求，实现期极易被当作缺陷「顺手修正」，导致与上游基准全面失配。

## 三、非目标

| 非目标 | 排除原因 |
|--------|----------|
| 混合语言检测（同一段文本输出多个语言及其占比） | 上游契约明确「每段文本只输出单一主语言」，且申报书已把混合语言检测列入明确不做项（`申报书-moon_langdetect-语种检测.md:39`）；本库的算法（n-gram 特征随机采样 + 逐轮归一化）天然收敛到单一主导语言，输出多语言占比需要不同的模型与训练数据，超出移植范围。 |
| 语言档案重训练管线（`LangProfile.add` / `omit_less_freq` / `update`） | 上游这三个方法在运行时**无任何调用点**（`docs/port/upstream-behavior-contract.md` §8.2「运行时只用 freq / n_words / name 三个字段，不调用 add / omit_less_freq / update」，机检命令 `grep -rn "omit_less_freq" langdetect/langdetect --include=*.py` 仅命中定义处与上游测试）；申报书亦明确不做（`申报书-moon_langdetect-语种检测.md:40`）；「模型即数据」定位下无训练需求。 |
| 方言 / 地区变体区分（en-GB / en-US、zh-Hans 之外的其他细分） | 上游只提供 `zh-cn` 与 `zh-tw` 两个中文变体档案，其余语言无变体档案（`docs/port/golden/expected.json` 的 `meta.langlist` 实测 55 项）；申报书明确不做（`申报书-moon_langdetect-语种检测.md:41`）；变体区分需要额外标注语料，属独立项目。 |
| 上游训练期 API 的移植（`load_json_profile`、`set_verbose` 的逐轮打印、`DetectorFactory.clear` 之外的工厂内部方法） | ADR 的 X 节已逐项裁决：`load_json_profile` 不移植（仅服务上游测试的注入路径，异常语义是把一切重包成 `FormatError(1)`，对产品无价值，`docs/port/architecture-decisions.md` X 节）；verbose 输出不移植（需 stdout 与 `%s`/`%.5f` 格式化，不影响检测结果）；移植这些 API 会引入无用户价值的兼容面，扩大验收面而不增加用户价值。 |
| 云端 / 外部服务形态的检测（把检测请求转发到服务端） | 与 G-05「检测全程离线」和申报书的离线嵌入定位（`申报书-moon_langdetect-语种检测.md:16`）直接冲突；一旦引入服务端调用，取值域、错误码、延迟口径全部改变，属另一产品形态。 |

## 四、用户故事

### 用户角色

- **应用开发者**：把语种检测嵌入自己的应用或内容管线，关心 API 是否简单、返回值是否可直接路由。
- **管线工程师**：处理多语言 UGC 入库，关心短文本 / 噪声输入下是否会得到看似确定实则错误的结果。
- **复现工程师 / 验收方**：把移植结果与上游 Python 基准做机器比对，关心数值是否逐位可比、随机性是否可控。
- **库维护者**：负责线上问题定位与包发布，关心失败是否可诊断、依赖是否可控。

### 用户故事

**【P0 - 必须】**

**US-01** 作为应用开发者，我想要一次调用就拿到一段文本的主语言代码，以便在多语言内容入库时立刻决定下游分词与排版策略。

- 验收标准：
  1. 已加载内置档案时，对 55 条中/长文本样本各调用一次主语言检测，55 条的返回值与样本预期语言一致（Yes/No）。
  2. 文本无任何可提取特征时，调用主语言检测，返回的不是语言代码，而是与上游一致的异常码 5（Yes/No）。
  3. 主语言检测的返回值只在 55 个语言代码范围内取值——对 250 条有概率输出的基准样本逐条核对，返回值落在该范围外的条数为 0（Yes/No）。

**US-02** 作为应用开发者，我想要同时拿到各语言的概率分布，以便在语言竞争激烈时按阈值决定是否信任主语言。

- 验收标准：
  1. 调用概率分布接口后，返回条目按概率从大到小排列——对 250 条有概率输出的基准样本逐条核对，出现降序反转的样本数为 0（Yes/No）。
  2. 返回条目中不存在概率小于或等于 0.1 的语言——对 250 条有概率输出的基准样本逐条核对，反例条数为 0（Yes/No）。
  3. 两个语言概率完全相同时，它们在返回列表中的先后顺序与内置档案的加载顺序一致——构造等概率场景，核对顺序（Yes/No）。

**US-03** 作为复现工程师，我想要在固定 seed 下得到与上游逐位一致的概率数值，以便把移植结果与上游基准做机器比对、并在回归时立刻定位偏差。

- 验收标准：
  1. native 目标下，固定 seed（0 与 42）对 250 条有概率输出的基准样本逐条调用概率分布接口，每条概率与基准 `prob_bits` 逐位一致；另对 18 条无特征样本核对异常码 5 一致（Yes/No）。
  2. 同一 seed、同一样本重复调用 5 次，输出逐次一致（对 14 组重复采样的组间差异数为 0，Yes/No）。
  3. js 与 wasm-gc 目标下同样调用，概率与基准的偏差落在已声明的容差内（Yes/No；容差取值见 10.5 待确认事项）。

**US-04** 作为管线工程师，我想要短文本得到显式的低置信提示，以便避免对过短输入硬猜语言而污染下游处理。

- 验收标准：
  1. 短文本（字符数 < 50）调用低置信接口时，返回的是低置信标记，而不是直接给出主语言（对 55 条短文本样本核对，直接给出主语言的样本数为 0，Yes/No）。
  2. 长文本（字符数 ≥ 50）调用同一接口时，返回正常的主语言结果（对 55 条中/长文本样本核对，走低置信分支的样本数为 0，Yes/No）。
  3. 同样的短文本调用主语言检测接口时，行为与上游一致（照常返回主语言或异常码 5），不受低置信接口影响（Yes/No）。

**US-05** 作为库维护者，我想要失败原因按成因给出稳定错误码，以便线上问题可被快速归类定位。

- 验收标准：
  1. 输入无特征时，抛出的异常携带错误码 5 且消息文本与上游一致（`No features in text.`，Yes/No）。
  2. 未加载任何档案就发起检测时，抛出的异常携带错误码 4 且消息文本与上游一致（`Need to load profiles.`，Yes/No）。
  3. 先验概率参数含负值或总和为 0 时，抛出的异常携带错误码 8，且两条成因的消息文本分别与上游一致（Yes/No）。

**US-06** 作为库维护者，我想要包内自带 55 种语言档案、不依赖外部数据文件，以便使用方在离线环境、任意工作目录下都能直接调用。

- 验收标准：
  1. 在空目录下、不设置任何数据路径环境变量的进程中调用检测接口，首次调用即可完成 55 个语言档案的加载（Yes/No）。
  2. 整个检测过程不读取用户提供的任何数据文件路径（检测过程中对外部数据文件的读取次数为 0，Yes/No）。
  3. 检测全程对外发起的网络请求数为 0（Yes/No）。

**【P1 - 重要】**

**US-07** 作为管线工程师，我想要控制送入检测的文本长度上限与语言先验，以便在固定长度预算与已知语种分布的管道里得到稳定结果。

- 验收标准：
  1. 设置文本长度上限为 N 后，超过 N 的输入只按不超过 N 个字符参与检测（Yes/No）。
  2. 提供只包含部分语言的先验权重时，不在先验中的语言其初始权重为 0，且先验权重之和归一化为 1（Yes/No）。

## 五、需求详细说明

### 5.1 功能需求（FR）

**公开能力面声明**：本库对外提供四类能力，均属本 PRD 范围，每类至少被一条 FR 覆盖。

1. **无状态便捷入口**：给定文本直接返回主语言代码；给定文本直接返回按概率降序的概率分布条目。
2. **可配置检测实例**：可设置随机种子、送入文本的长度上限、语言先验权重；同一实例可重复送入文本。
3. **可用语言列表查询**：返回当前已加载的语言代码集合。
4. **低置信入口**：字符数过短的文本返回低置信标记，而不是直接给出主语言。

对应关系：第 1 类 → FR-01 / FR-02 / FR-03 / FR-04 / FR-12；第 2 类 → FR-05 / FR-06 / FR-07 / FR-08 / FR-09 / FR-10 / FR-19 / FR-20；第 3 类 → FR-13；第 4 类 → FR-21 / FR-22 / FR-23。

### 5.2 非功能需求（NFR）

| 类型 | 需求描述 | 衡量标准 |

| 性能 | 单次检测的响应时延在交互式管线可接受范围内 | 在 native 目标、已加载档案的进程中，对短文本（26 字符）、英文长文本（261 字符）、中文长文本（85 字符）各连续调用 30 次，取中位数；目标：冷启动（首次加载 55 个档案）中位数不超过 1 秒，单次检测中位数不超过 5 毫秒。参照实测量级：上游 Python 冷启动中位数 303.70 毫秒、单次检测中位数 0.80 / 1.69 / 1.06 毫秒（`docs/port/golden/timing.json`）。 |
| 兼容性 | 目标运行时逐项行为（栏 1）+ 能力边界（栏 2），两栏口径并列，不以「构建退出码为 0」替代 | 栏 1「逐项行为」：native、js、wasm-gc 三个目标逐一核对——(a) 检测接口对 55 条长文本样本给出与预期一致的主语言；(b) 无特征输入返回异常码 5 而非语言代码；(c) 可用语言列表长度为 55；(d) 55 个语言的档案条目数合计 184129。栏 2「能力边界」：native 目标声明为逐位一致档（概率与基准 `prob_bits` 逐位一致）；js 与 wasm-gc 声明为容差档（因该两目标下自然对数实现路径与 native 不同，逐位不可达），其容差取值待校准（见 10.5），在容差取值落定前该两目标只按栏 1 的 (a)–(d) 判定。 |
| 安全性 | 检测全程本地执行，零网络请求；不读取用户数据文件；不写任何外部状态 | 用网络计数手段观察一次完整检测（含首次加载）前后的对外连接数，新增连接数为 0（Yes/No）；监控文件访问，对内置档案以外的读取次数为 0（Yes/No）。 |

### 10.1 术语表

| 术语 | 定义 |
|------|------|
| 语种检测 | 判定一段文本所属自然语言的单一主语言（上游契约：每段文本只输出单一主语言） |
| n-gram | 连续 1~3 个字符组成的特征片段；上游用 1/2/3 元组频率做朴素贝叶斯式评分 |
| 语言档案 | 一种语言一个文件，含该语言名、三类 n-gram 的总次数、各 n-gram 的频率表（55 个语言共 184129 条频率条目） |
| 概率分布接口 | 返回语言与概率条目列表的接口；上游名为 `detect_langs` |
| 主语言检测接口 | 返回单一语言代码的接口；上游名为 `detect` |
| 逐位一致（位级一致） | 两个浮点数值的 IEEE754 双精度二进制表示完全相同（大端十六进制串相等） |
| 容差档 | 允许浮点数值存在有限偏差的验收口径，偏差阈值须实测后校准 |
| 低置信 | 输入过短或特征不足时，系统给出「无法可靠判定」的显式标记，而不是给出一个主语言 |
| 上游 quirk | 上游实现中非直觉但已构成行为契约的表现（如 URL 吞词、空输入抛异常码 5），移植后必须保持 |
| 可用语言数 | 有效语言档案的个数（实测 55）；与概率向量长度不是同一个量 |

### 10.6 PRD 拆分声明（必填，不写「无」）

**单份 PRD，无需拆分。**

| 归属 | 覆盖单元 | 共享接口/边界（与兄弟 PRD 对齐） | spec 承接 |
|------|----------|----------------------------------|-----------|
| 单份 PRD，无需拆分 | 本 PRD 全部（FR-01 至 FR-26） | 无 | 单个 spec |

判定说明：本需求是**单一库的单一能力**——一个 `detect` / `detect_langs` 的 API 面加一份内置档案数据，不存在 ≥2 个独立子系统，因此没有可按子系统切分的拆分轴。按「数据面 / 实现面」横切会产生**验收死锁**：实现单元的验收标准（如 FR-01 主语言一致、FR-02 概率排序）必须依赖数据单元已交付，而数据单元单独交付时不构成用户可用的交付物——它既不能被用户调用，也没有独立的用户价值，无法独立通过交付验收。故不采用时序/分层拆分轴。任务量级由本 PRD 内的 FR 粒度控制（FR-01 至 FR-26 每条均可独立开发、独立验收），交付顺序属后续计划阶段，不在 PRD 决定。

### 10.7 敏感数据流声明

无。

说明：本库不处理可定位到个人的数据，也不进行任何跨边界外传；检测全程在调用方进程内本地执行、零网络请求（见 §5.2 安全性行：一次完整检测的对外新增连接数为 0，对内置档案以外的文件读取次数为 0）。数据方向裁决为「设备内闭环」——输入文本只在调用方进程内被读取用于特征提取，不落盘、不上报、不外传。
